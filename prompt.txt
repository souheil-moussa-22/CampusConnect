# 3. MANDATORY ARCHITECTURE: CLEAN ARCHITECTURE

The entire project MUST follow Clean Architecture.

Do not simply organize files into folders named Domain, Application, Infrastructure, and Presentation. Implement genuine separation of responsibilities and dependency inversion.

## 3.1 Domain Layer

The Domain Layer contains the core business logic.

It must be independent of all external technologies.

Responsibilities:
- Business entities.
- Value Objects.
- Domain services.
- Domain enums.
- Business invariants.
- Domain exceptions.
- Repository contracts when appropriate.

Examples:
- User.
- StudentProfile.
- HelpRequest.
- HelpProposal.
- StudySession.
- Review.
- Notification.
- Report.

The Domain Layer must NOT import:
- React.
- Next.js.
- Prisma.
- PostgreSQL libraries.
- Auth.js.
- UI components.

All business rules must be independent of frameworks and databases.

## 3.2 Application Layer

The Application Layer coordinates business operations through Use Cases.

Responsibilities:
- Use Cases.
- Application services.
- DTOs.
- Repository interfaces.
- External service interfaces.
- Authorization policies.
- Application-level validation.
- Transaction orchestration.

Examples of Use Cases:

Authentication and Users:
- RegisterUser.
- AuthenticateUser.
- UpdateStudentProfile.
- GetStudentProfile.

Requests:
- CreateHelpRequest.
- UpdateHelpRequest.
- DeleteHelpRequest.
- GetHelpRequest.
- SearchHelpRequests.
- CompleteHelpRequest.

Proposals:
- CreateHelpProposal.
- AcceptHelpProposal.
- RejectHelpProposal.
- GetReceivedProposals.

Sessions:
- CreateStudySession.
- CompleteStudySession.
- CancelStudySession.
- GetStudentSessions.

Reviews:
- CreateReview.
- GetStudentReviews.

Notifications:
- GetNotifications.
- MarkNotificationAsRead.
- MarkAllNotificationsAsRead.

Reports:
- CreateReport.
- GetReports.
- ModerateReport.

Matching:
- RecommendStudents.
- CalculateCompatibilityScore.

Each Use Case must have a clearly defined responsibility.

Never access Prisma directly inside a Use Case.

Never place React components or Next.js logic inside this layer.

## 3.3 Infrastructure Layer

This layer implements the technical details and external dependencies.

Responsibilities:
- Prisma repositories.
- PostgreSQL persistence.
- Database mappers.
- Authentication adapters.
- Notification persistence.
- Transaction management.
- External service integrations.

Examples:
- PrismaUserRepository.
- PrismaHelpRequestRepository.
- PrismaHelpProposalRepository.
- PrismaStudySessionRepository.
- PrismaReviewRepository.
- PrismaNotificationRepository.

Repository implementations must implement interfaces defined by the inner layers.

Keep Prisma models separate from Domain entities.

Use explicit mapping between database models and Domain objects.

## 3.4 Presentation Layer

This layer handles communication with users.

Responsibilities:
- Next.js pages.
- React components.
- Server Components.
- Client Components.
- Server Actions.
- Route Handlers.
- Form schemas.
- UI state management.
- HTTP response handling.

Presentation must invoke Application Use Cases through a composition root or dependency injection mechanism.

Do not implement business rules inside React components, Server Actions, or Route Handlers.

## 3.5 Dependency Rule

Respect this dependency direction:

Presentation → Application → Domain

Infrastructure implements interfaces defined by Application or Domain.

The Domain must never depend on external layers.

Apply:
- SOLID principles.
- Dependency Inversion Principle.
- Repository Pattern.
- Use Case Pattern.
- Separation of Concerns.
- Dependency Injection.

Avoid circular dependencies, unnecessary abstractions, and overengineering.

# 6. FUNCTIONAL REQUIREMENTS

## MODULE 1 — Authentication and Student Profiles

- Password hashing when using credentials authentication.
- Protected routes.
- Role-based authorization.

- ADMIN.

Student profile fields:
- First name.
- Last name.
- Email.
- Profile picture.
- Academic specialty.
- Academic level.
- Biography.
- Skills.
- Availability.

Students can update only their own profiles.

## MODULE 2 — Help Requests

Students must be able to:
- Create requests.
- Update their own requests.
- Delete their own requests.
- View request details.
- View their published requests.
- Browse other students' requests.

Request fields:
- Title.
- Description.
- Subject.
- Required academic level.
- Availability.
- Author.
- Publication date.
- Status.

Statuses:
- OPEN.
- HELP_ACCEPTED.
- COMPLETED.

## MODULE 3 — Search and Filtering

Implement real database-based filtering.

Filters:
- Subject.
- Academic level.
- Status.
- Keyword.

Features:
- Combined filters.
- Search.
- Sorting.
- Pagination.
- Reset filters.

Do not simulate filtering using static frontend data.

## MODULE 4 — Help Proposals

Students can propose their help on other students' requests.

Proposal fields:
- Request.
- Student.
- Motivation message.
- Creation date.
- Status.

Statuses:
- PENDING.
- ACCEPTED.
- REJECTED.

Business rules:
- A student cannot help themselves on their own request.
- A student cannot submit duplicate proposals.
- Only the request owner can accept or reject proposals.
- Completed or closed requests cannot receive proposals.
- Only one proposal can be accepted per request.

When a proposal is accepted, execute an atomic workflow:

1. Verify authorization.
2. Verify request and proposal statuses.
3. Accept the selected proposal.
4. Reject all other pending proposals.
5. Update the request status.
6. Create the study session.
7. Create notifications.

## MODULE 5 — Study Sessions

Create sessions after proposal acceptance.

Session fields:
- Related request.
- Request owner.
- Helping student.
- Date.
- Time.
- Duration.
- Meeting mode.
- Location or meeting URL.
- Status.

Statuses:
- SCHEDULED.
- COMPLETED.
- CANCELLED.

Features:
- Upcoming sessions.
- Past sessions.
- Session details.
- Session completion.
- Session cancellation.

Completing a session must update the associated request to COMPLETED.

## MODULE 6 — Reviews and Ratings

Allow participants to review each other after a completed session.

Review fields:
- Reviewer.
- Reviewed student.
- Session.
- Rating from 1 to 5.
- Comment.
- Creation date.

Rules:
- Only session participants can submit reviews.
- The session must be completed.
- No self-reviews.
- No duplicate reviews for the same participant and session.

Display:
- Average rating.
- Review count.
- Comments.
- Contribution history.

## MODULE 7 — Student Dashboard

Display real database statistics:

- Published requests.
- Submitted proposals.
- Received proposals.
- Completed sessions.
- Upcoming sessions.
- Average rating.

Add:
- Recent activity.
- Active requests.
- Pending proposals.
- Upcoming sessions.
- Recent notifications.

## MODULE 8 — Administration

Create a protected administrator area.

Features:
- View reported publications.
- Inspect reports.
- Review report reasons.
- Hide or restore publications.
- Resolve reports.
- View users.
- Suspend or reactivate accounts.

Only ADMIN users may access these operations.

## MODULE 9 — Notifications

Implement internal notifications.

Events:
- Proposal received.
- Proposal accepted.
- Proposal rejected.
- Session created.
- Session updated.
- Session cancelled.
- Session completed.
- Review received.
- Report moderated.

Notification fields:
- Recipient.
- Type.
- Message.
- Creation date.
- Read status.

Add a notification dropdown with unread count and notification history.

## MODULE 10 — Original Feature: Smart Matching

Implement an intelligent student recommendation system.

The objective is to recommend students who are likely to help with a particular request.

Calculate a compatibility score using:
- Skills matching.
- Specialty matching.
- Academic level compatibility.
- Availability overlap.
- Student ratings.

Return:
- Student profile.
- Matching skills.
- Average rating.
- Compatibility percentage.
- Explanation of matching criteria.

Use a transparent weighted scoring algorithm.

Do not introduce an external AI model unless genuinely necessary.

The matching logic must belong to the Application or Domain Layer, not React components.
